## 概述

在 AI 编程工具日益普及的今天，如何让 AI 生成符合预期的代码、如何管理 AI 生成的变更、如何确保团队协作的一致性？这些问题逐渐成为开发者面临的挑战。**OpenSpec** 正是为解决这些问题而生的规范驱动开发框架。

OpenSpec 是一个专为 AI 编程助手设计的开发工作流框架，其核心理念是：**"先写规范，再写代码"**。通过结构化的规范文档，AI 能够准确理解需求，减少生成代码的随机性和错误率。

## 问题：AI 编程的痛点

在日常使用 AI 编程助手（如 Claude Code、Cursor、Copilot 等）时，开发者经常遇到以下问题：

### 1. AI 生成的代码不符合预期

AI 生成的代码经常出现"对不上"的情况：要么功能实现有偏差，要么代码风格与项目不一致，要么遗漏了边界条件处理。这是因为 AI 缺乏对项目整体需求的理解，只能根据当前对话的上下文"猜测"需求。

### 2. 变更难以追溯和管理

AI 生成的代码变更散落在各处，缺少系统性的变更记录。当需要回溯某个功能的决策过程或修改原因时，往往无从查起。

### 3. 团队协作不一致

不同开发者使用 AI 工具的方式各不相同，导致代码风格、架构设计存在较大差异，团队协作成本增加。

### 4. AI "幻觉"问题

AI 有时会编造不存在的 API、错误的配置或不可行的技术方案，给开发带来额外排查成本。

## 解决方案：OpenSpec 的核心理念

OpenSpec 通过**规范先行**的方式，让 AI 在编写代码之前先"学习"项目的需求和约束，从根本上提升 AI 生成代码的质量。

### 规范驱动的工作流程

OpenSpec 的核心理念可以概括为一个闭环流程：

```
共识规范(Spec) → AI 执行 → 自动验证 → 迭代与归档
```

1. **共识规范**：人类与 AI 共同撰写结构化的需求规范
2. **AI 执行**：AI 根据规范自动生成代码、文档或变更提案
3. **自动验证**：框架内置的验证器依据规范中的测试用例进行检查
4. **迭代与归档**：形成完整的变更历史，便于审计和迭代

### OpenSpec 的核心价值

| 核心价值 | 说明 |
|---------|------|
| 规范先行 | 在编写代码之前，先明确"要构建什么"以及"为什么" |
| 变更可视化 | 所有变更以提案形式呈现，便于审查和批准 |
| AI 友好 | 为 AI 提供清晰的工作边界和上下文 |
| 可追溯性 | 完整的变更历史，便于回溯和审计 |

## 使用方法

### 安装

OpenSpec 需要 Node.js ≥ 20.19.0 环境。

```bash
# 全局安装 OpenSpec CLI
npm install -g @fission-ai/openspec@latest

# 验证安装
openspec --version

# 查看帮助
openspec --help
```

### 初始化项目

在项目根目录下执行初始化：

```bash
cd your-project
openspec init
```

初始化过程会：
- 询问您使用的 AI 工具（Claude Code、Cursor、Trae 等）
- 自动配置相应的斜杠命令
- 创建 `openspecpec/` 目录结构
- 生成 `AGENTS.md` 文件（AI 助手规则）

### 初始化后的目录结构

```
your-project/
├── .claude/              # Claude Code 配置
│   └── commands/
│       └── openspec/
│           ├── apply.md   # 执行已批准的变更
│           ├── archive.md # 归档已完成的变更
│           └── proposal.md # 发起新变更提案
├── openspec/
│   ├── specs/            # 当前系统规范
│   ├── changes/          # 新功能变更
│   ├── AGENTS.md         # AI 助手规则
│   └── config.yaml       # 配置文件
```

### 核心概念

OpenSpec 的核心概念包括以下几个工件（Artifacts）：

#### 1. Proposal（提案）
回答"为什么"，定义变更的价值和范围。在变更的第一步创建。

#### 2. Specs（规范）
回答"做什么"，用可测试的方式定义需求。包含详细的功能描述、输入输出、边界条件等。

#### 3. Design（设计）
回答"怎么做"，记录技术决策和方案。在规范之后创建。

#### 4. Tasks（任务）
回答"做哪些"，将工作分解为可执行步骤。在设计之后创建。

### 工作流程

#### 1. 发起变更提案

使用 `/openspec:proposal` 命令发起新提案，AI 会根据 `proposal.md` 中的规范生成提案文档。

#### 2. 编写规范文档

创建 `openspec/changes/<变更名>/proposal.md`、`specs/`、`design.md` 等文档，清晰地定义需求和实现方案。

#### 3. 生成任务清单

使用 `/openspec:ff` 命令让 AI 生成实施任务清单。

#### 4. 执行任务

按照任务清单逐项执行，AI 会参考规范和设计文档生成代码。

#### 5. 归档变更

完成开发后，使用 `/openspec:archive` 命令归档变更，形成完整的变更历史。

### 适用场景

OpenSpec 适用于以下场景：

1. **新项目启动**：从一开始就用规范定义需求，确保 AI 生成符合预期的代码
2. **功能增强（迭代项目）**：在现有代码库基础上添加新功能，通过规范管理变更
3. **多人协作**：团队成员使用统一的规范和工作流程，减少协作成本

## 与传统开发模式的对比

| 维度 | 传统开发 | 使用 OpenSpec |
|------|---------|--------------|
| 需求定义 | 口头或文档描述，容易歧义 | 结构化规范，减少歧义 |
| AI 生成代码 | 随机性高，质量不稳定 | 规范约束，质量可控 |
| 变更管理 | 散落各处，难以追溯 | 统一管理，完整历史 |
| 团队协作 | 各自定义，风格不一 | 统一规范，协作顺畅 |

## 总结

OpenSpec 通过**规范驱动**的方式，为 AI 编程提供了一个系统化的开发框架。它解决了 AI 编程中的核心痛点——代码质量不稳定、变更难以追溯、团队协作不一致——让 AI 真正成为可靠的编程助手。

如果你在使用 AI 编程助手时遇到类似问题，不妨尝试一下 OpenSpec，体验规范驱动开发的优势。
